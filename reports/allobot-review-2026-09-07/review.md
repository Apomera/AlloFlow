**Priority fixes**

P1 means fix before expanding the workflow; P2 means a concrete reliability or usability defect worth fixing next. “Runtime” below means the shipped module was exercised locally with mocked host/provider dependencies. “Code trace” identifies a deterministic path in the source, without claiming a full browser reproduction.

1. **P1 — Two Blueprint commands discard the parameters they need.** Runtime verified.

   `rebuild_lesson_step` reads a step number, and `apply_lesson_template` reads a template name. Neither has a parameter declaration in `PLAN_CONTRACTS`. `sanitizeCommandParams` consequently replaces supplied values with `{}`. Calling the public execution API with `{step: 3}` yields “Which step?”; supplying a valid template name yields “Which template?” Neither host callback runs.

   Evidence: [allo_commands_source.jsx:618](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/allo_commands_source.jsx:618>), `:643`, `:977`, `:993`. The current tests in [tests/blueprint_commands.test.js:123](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/tests/blueprint_commands.test.js:123>) and `:144` call `.run()` directly and bypass the sanitizer.

   Refinement: declare canonical `step` and `name` parameters; validate their type and bounds; normalize supported aliases before filtering. Exercise both commands through `runCommandById` and the router. When correcting the step contract, also replace the host's out-of-range clamping at [AlloFlowANTI.txt:45402](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/AlloFlowANTI.txt:45402>) with an explicit “step not found” response, so step 99 cannot select the last real row.

2. **P1 — A question about a Blueprint can still revise it.** Runtime verified.

   “Why did you choose a glossary?” is answered correctly. “Why include a glossary?” and “Would you change anything about this plan?” invoke the reviser, even when `detectWorkflowIntent` explicitly returns `QUESTION`. The word list containing `include` and `change` overrides that classification.

   Evidence: [udl_chat_source.jsx:1278](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:1278>), `:1295`, `:1317`; observations `blueprint-question`.

   Refinement: let explicit question intent and the question lane take precedence. Apply edits only for an actual edit request. Add contrastive examples such as “Why include X?” versus “Include X,” and “Would you change X?” versus “Change X.” The visible “Ask about this plan” lane already exists; make ordinary questions equally safe.

3. **P1 — Typed multi-step plans use a context getter from the starting render.** Code trace, supported by a simulated render transition.

   The host passes its render-scoped `_alloCmdCtx` into the chat controller. The controller repeatedly invokes that same function while a plan runs. A React rerender creates a newer function and publishes a newer context, but the existing async plan still has the old function. A source-generation step can finish while the next step still sees `hasSourceOrAnalysis: false`, or later actions can use old settings/content callbacks. Calling the old getter also overwrites `_alloCmdCtxRef.current` with old state.

   Evidence: [AlloFlowANTI.txt:44298](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/AlloFlowANTI.txt:44298>), `:45346`, `:45799`, `:46091`, `:49577`; [udl_chat_source.jsx:2581](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2581>). Other host consumers already read `_alloCmdCtxRef.current`.

   Refinement: supply a stable getter that reads the latest published context, and ensure producer completion exposes committed source/settings before a dependent step starts. Verify source → analysis → quiz, grade change → generation, and role changes during execution through the real host integration. The included simulation demonstrates the stale callback failure; it is not a full React-app reproduction.

4. **P1 — “Run lesson Blueprint” reports command completion before generation completes.** Runtime verified.

   Its synchronous `run` handler calls `c.runBlueprint()` and discards the returned promise/result. Even `runCommandById(..., {awaitCompletion: true})` returns while generation is unresolved. `runPlan` therefore has no way to await this work or observe a blocked/failed Blueprint through that command. The command also inherits default planning metadata rather than declaring its execution semantics.

   Evidence: [allo_commands_source.jsx:939](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/allo_commands_source.jsx:939>), `:943`, `:618`, `:3383`; the host returns the real promise at [AlloFlowANTI.txt:45393](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/AlloFlowANTI.txt:45393>).

   Refinement: use the shared asynchronous command lifecycle, translate the Blueprint run record into an explicit result, and declare requirements, review/interaction behavior and whether following steps are allowed. Cover blocked generation planning, partial output, failure, completion, and a dependent next step. A launch acknowledgment should remain visibly distinct from completed generation.

5. **P2 — “Undo plan” is offered without an undo snapshot.** Runtime verified.

   `planAndSendUdlMessage` calls `captureIntentSnapshot` and `restoreIntentSnapshot`, but neither is in its scope or its host dependency bag. The capture exception is swallowed and clears the snapshot. A successful run still offers Undo; clicking it says there is nothing to undo. If a snapshot is manually present, restoring settings is silently skipped while the UI claims both content and settings were restored.

   Evidence: [udl_chat_source.jsx:2297](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2297>), `:2360`, `:2573`, `:2593`; [AlloFlowANTI.txt:46090](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/AlloFlowANTI.txt:46090>).

   Refinement: explicitly wire both helpers; report partial restoration honestly; offer Undo only when a valid snapshot exists. Preserve the initial snapshot on resume. Consider detecting intervening manual edits before restoring an old snapshot.

6. **P2 — Chat marks unavailable, failed, and pending commands as successful.** Runtime verified.

   The confirmation handler unconditionally prefixes the result with a green check and falls back to “Done.” A now-unavailable command returning `null` produces “✅ Done.” An error result produces “✅ Provider failed.” Pending work produces “✅ Working...”

   Evidence: [udl_chat_source.jsx:2388](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2388>); observations `unavailable-confirm`, `failed-confirm`, `pending-confirm`.

   Refinement: render the actual result status. Handle unavailable, needs-input, pending, success, partial, cancelled, and error separately; associate async completion with the same visible operation. Use one result formatter for chat, voice and palette.

7. **P2 — Saving a command workflow intercepts Cancel and Back.** Runtime verified.

   While waiting for a name, the save-name branch runs before `_isSkip` and `_isShow`. Typing `cancel` attempts to save under the name “cancel.” Clicking “Back to current plan” passes `__allo_plan_show` to the save service as a name. The probe records the attempted save; it deliberately mocks storage to avoid creating either artifact.

   Evidence: [udl_chat_source.jsx:2429](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2429>), `:2481`, `:2509`, `:2543`.

   Refinement: process cancellation and control actions before free-text data. Replace the overlapping `editing`/`saving`/`libraryOnly` flags with one explicit review state. Test Save → Cancel, Save → Back, blank names, failed storage, and a name that happens to be “yes.”

8. **P2 — The plan's Stop button disables itself when progress arrives.** Code trace.

   The running message contains “Stop after current step,” but the next progress message makes that chooser historical. The renderer disables every choice button except those in the last message. The visible Stop control therefore becomes disabled as soon as a step starts. Typed `stop` still works.

   Evidence: [udl_chat_source.jsx:2577](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2577>), `:2584`; [view_misc_modals_source.jsx:283](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/view_misc_modals_source.jsx:283>).

   Refinement: put active-run controls in a persistent operation card or footer, outside transcript recency rules. Also reconcile the wording: the UI says it will finish the current step, while the executor passes stop requests to the active command's cooperative cancellation watcher ([allo_commands_source.jsx:3046](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/allo_commands_source.jsx:3046>), `:3383`). Choose and accurately explain the intended behavior.

9. **P2 — Standard conversation failures can produce no visible reply.** Runtime verified.

   `_generateStandardChatResponse` catches provider errors and only logs them. It resolves without adding an error message or propagating the failure to the caller. During a Blueprint question, the outer handler may subsequently show “The plan above is unchanged” without answering or explaining the failure.

   Evidence: [udl_chat_source.jsx:382](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:382>), `:391`, `:1300`; observation `chat-provider-failure` logged one warning and zero messages.

   Refinement: preserve the question and show a concise failure with Retry. Return a structured failure or let the caller handle it once. Avoid duplicate messages between the helper and outer chat handler.

**Product refinements after these fixes**

- **Keep one active plan visible, with a stable identity.** Every historical `type: 'blueprint'` marker currently renders the same global `activeBlueprint` and run record ([view_misc_modals_source.jsx:242](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/view_misc_modals_source.jsx:242>)). Multiple plans in one conversation can therefore show repeated copies of today's plan in old positions. Store a plan ID/revision on messages, render historical summaries, and place the active editable plan beside or above the conversation. Keep the existing row statuses, resource previews and diagnostics.

- **Allow questions without losing a command workflow.** Lesson Blueprints have Generate / Change / Ask lanes. Saved command workflows offer Run / Edit / Save / Just chat; other text clears the pending workflow ([udl_chat_source.jsx:2626](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2626>)). A new command after a review card also bypasses the main router because any last `choices` message suppresses it (`:2633`). Track which interaction owns a reply, retain the draft when the user asks about it, and provide an explicit way to switch tasks. Give both plan types comparable Review / Ask / Edit / Run behavior while preserving their different purposes.

- **Make command parameters a real schema.** The current contract is an allow-list, with no required/default/range model; the plan card explicitly acknowledges this at [udl_chat_source.jsx:2242](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2242>). Use one schema to drive router extraction, validation, readable review labels, parameter editing and examples. Show effective values such as grade and language and whether they came from the request or current settings. This prevents a card marked “[ready]” from immediately asking for missing information.

- **Let a detailed lesson brief reach the planner.** `planUtterance` returns `null` for requests longer than 400 characters ([allo_commands_source.jsx:3277](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/allo_commands_source.jsx:3277>)). A realistic brief containing topic, standards, learner needs and output requests can exceed this easily. Use a deliberate input budget, preserve stated constraints, and surface a clear response when the limit is exceeded. Silent fallback into ordinary conversation makes supported workflow scope hard to discover.

- **Reduce conversational ceremony where the answer is already clear.** The standard chat prompt requires discovery, a separate permission-to-deliver step, and a rigid strategy format ([udl_chat_source.jsx:361](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:361>)). That can make a specific question during plan review feel like restarting an intake interview. Reserve discovery for missing information and review for changes or generation; answer concrete questions directly. Validate this with representative teacher conversations before changing the prompt broadly.

- **Finish localization of the command workflow experience.** Much of the new save/edit/library copy and parsing is English-only ([udl_chat_source.jsx:2429](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/udl_chat_source.jsx:2429>), `:2503`; [agent_core_blueprint_service_module.js:800](<C:/Users/cabba/OneDrive/Desktop/UDL-Tool-Updated/agent_core_blueprint_service_module.js:800>)). Move visible text into existing translation keys and use structured step-edit controls that work independently of English command phrasing. Keep natural-language editing as an additional input route.

**Suggested implementation order**

1. Repair parameter contracts, question routing, undo dependencies, result status and save/cancel precedence. Add regressions at public module boundaries.
2. Repair fresh context and asynchronous Blueprint execution. Exercise producer/consumer chains against the actual React host, including completion, failure, cancellation and resumption.
3. Introduce a persistent active plan/operation card with stable IDs and explicit review states. This addresses disabled Stop, repeated Blueprint cards, lost drafts and fragmented status.
4. Refine input budgets, parameter forms, conversational behavior and localization using a short set of realistic teacher scenarios.

This can be delivered incrementally. There is no need to replace the existing planner, generation matrix, template library or command registry.

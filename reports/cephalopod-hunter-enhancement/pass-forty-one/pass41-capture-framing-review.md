# Pass41 capture framing source review

Read-only review of `capture-crabs.cjs`, its saved manifests, and runtime initialization/crab update paths. No tests, browser/server/GPU jobs, or repository changes were performed.

The low red images are not a matched A/B pair. The saved baseline yaw is 5.804436323003885 radians; current yaw is 5.007185325810618 radians. Position and scale match, but world bounds and the camera derived from those bounds/orientation consequently differ. Keep exact pose/camera equality as the acceptance rule. Retain both raw captures, show the current low image only as a standalone low-profile rendering smoke result, and report the five balanced matched pairs as the A/B evidence.

The capture's first zero-delta call is not a mutation-free state. Its patched Clock.getDelta queues Escape in a microtask and returns 0. The runtime calls loop synchronously during initialization; its active branch finishes before that queued Escape can run. Crab spawn sets wanderTimer to 0. The first active crab update therefore satisfies `wanderTimer <= 0`, consumes two seeded random draws, changes wanderAngle, assigns a new timer, and copies that heading into rotation.y, despite dt=0. Leg child offsets and several other non-time-driven initialization/update decisions also execute. The later pause freezes that already-updated pose, rather than pausing before all simulation update work. The manifest wording “pause before simulation ticks” is therefore too strong; “zero elapsed game time followed by native Escape pause” describes the mechanism accurately.

This explains why zero elapsed time is insufficient as a substitute for checking the actual captured actor state. It does not, by itself, prove the exact cause of the two different low headings. The RNG is local and seeded inside initHuntSim3D; spawn and the first update are unchanged by pass41's literal guards, and the new shader/material functions add no local RNG draws. Equal seed, identical initialization state and identical active-update execution would be expected to produce the same heading. The saved artifacts do not record the initial wanderAngle, wanderTimer, randomState, pre-pause active iteration count or all conditional RNG consumers, so attributing the discrepancy specifically to a different first-tick draw or timing path would be speculation. Source proof and geometry checks remain valid, but cannot make this unmatched low image pair comparable.

One capture metadata detail also limits actor-index interpretation: `selected.index` is recorded from the initial rock selection and copied into every frame. Later views switch the selected object by type without updating that index. Thus low/red's `index: 0` is the initial rock index, not a recorded red actor index; balanced hermit views similarly retain the initial rock index. The actual recorded type, position, rotation, scale, bounds, camera and camera target are the useful frame identity/framing evidence here. For future captures, record each view's actual crab-array index/name or a stable authored actor identity, as well as pose and framing; do not relax those equality checks.

No further runtime change or new capture is necessary to finish this pass when the unmatched low frame is explicitly excluded from A/B claims. The root's strict framing audit and revised gallery/report treatment correctly preserve the evidence and its limits.

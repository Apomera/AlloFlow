For school IT: check a packet in ten minutes

A packet is one HTML file that holds a short practice activity or a short check. The questions, the recorded sounds and the scoring are inside the file, so it runs in a web browser with no internet connection. At the end the learner can save a results file to the device, and a teacher opens that file in a spreadsheet.

Where the data goes

  1. A teacher makes the file on their own device: on the maker page of this site, or inside the AlloFlow app. The maker page puts the file together in the browser. The words and the choices are not uploaded.
  2. The file reaches the learner by a channel the school already uses, such as its learning platform, email or a shared drive. These pages have no way to deliver a file.
  3. The learner opens the file in a browser. The learner's place, answers and the time on each item are kept in that browser's local storage, on that device.
  4. At the end the learner presses a button to save a results file to the device: CSV for a spreadsheet, or JSON. Saving sends nothing.
  5. The learner hands the results file to the teacher, again by the school's own channel.
  6. If the teacher wants, the results files are added up in a spreadsheet, or on the Add up results page, which cannot connect to anything.

Check it yourself

None of these steps asks you to trust this site. Each uses the file itself and your own browser.

  1. Read the report. Put the file on Check a file. It reads the file as text in your browser and lists the policy, the script hashes and every construct that could reach out, with line numbers. Then confirm by hand:
  2. Find the policy line. Open the file in a text editor. Near the top is <meta http-equiv="Content-Security-Policy" content="...">. That is the policy the browser enforces on this file.
  3. Read the policy. default-src 'none' refuses everything the policy does not name. connect-src 'none' refuses every connection a script can make: fetch, XMLHttpRequest, WebSocket, EventSource and sendBeacon. img-src data: and media-src data: blob: allow only pictures and sounds held in the file. form-action 'none' and base-uri 'none' block forms and a base address.
  4. Check the script hash. script-src 'sha256-...' lets one script run: the one whose SHA-256 is that value. The file has one script. Change a character of it and the browser refuses to run it. A matching hash shows that the file agrees with itself, not who made it: a person who changes a file on purpose can change the hash too, and the policy still limits what that file can reach. The report also gives a hash of the code without its data block: two files made the same way, with the same activities, show the same value, so code that was read once does not have to be read again.
  5. Search for what a policy cannot stop. A policy cannot stop a page from being sent to another address. Search the file for location, open(, <form and http. In a packet with no class mailbox, the code uses location once, to read the learner's code name after # in the file's own address, and http appears only in http-equiv. A file with a class mailbox also holds the address of its mailbox.
  6. Run it and watch. Open the file with the browser's developer tools on the Network tab, or with the network unplugged, and complete it. No request leaves the device.
  7. Find the saved place. In the developer tools, open Application (Chrome, Edge) or Storage (Firefox, Safari), then Local Storage. There is one key, named alloflow-take-home: then the packet id, a colon and the version. To clear it, press Start over in a practice file, delete the key, or clear the browser's site data. A check keeps the learner's label and a count of tries after Start over, so clear a check in the browser.

The facts, for a privacy review

What is collected A label the learner types (a code name or a first name; it can be left blank), each answer, the time on each item, and the start and finish times from the device clock, with its offset from UTC. Each run also gets a random session number. Nothing else: no email address, no account, no details of the device or the browser, no location.
Where it is stored In the browser's local storage on the learner's device, and in any results file the learner saves.
Who can read it Anyone who uses that browser on that device, and anyone who is given the results file. Neither is encrypted. The answers of a practice file can be read in its source. The answers of a check are scrambled, which stops casual looking only. A teacher code locks the review screen of a check; it is not encryption.
What leaves the device, and when Nothing, unless a person passes on a saved results file. There is one exception: the class mailbox kind of practice file, in the next row.
The class mailbox kind A practice file made inside the AlloFlow app by a teacher who has set up a class mailbox has a Send button. When the learner presses Send, the results go to that class mailbox, a Google Apps Script web app at script.google.com, and nowhere else. How to recognize one: the report on Check a file starts "This file can send results to one place", the policy's connect-src names script.google.com, and About this file says so. Files made on this site's maker page have no mailbox. Checks are made with no mailbox.
What this site's server can see When someone uses these pages: ordinary web requests for the pages, their scripts and, on the maker page, the sound files, with what every web request carries, such as the IP address and the time. Most sound files are the same whatever is chosen. Some words have their sounds in small files of about 40 words each, and the maker page asks only for the ones it needs: the server can see which of those files were asked for, not which words. Never the words or the choices, and never results. If a school puts a packet on its own web server, that server sees requests for the file and nothing the learner does in it.
Accounts, cookies, analytics None on these pages: no sign-in, no cookies, no analytics or tracking scripts. Each page lists every file it loads under See the details. In the browser, the maker page keeps the teacher's last choices and the sound files, the results page keeps results only if a switch is turned on, and this page and Check a file keep nothing.
How long it is kept As long as the school keeps the files. The saved place stays in the learner's browser until it is cleared. This site holds no copy, because nothing is sent to it. Results sent to a class mailbox are held by that mailbox; ask the teacher who set it up.

Known limits

  • A results file can be edited. The check value inside it finds accidental changes, not deliberate ones.
  • Times come from the clock of the learner's device.
  • A packet is for practice and for checking progress. It is not a locked test: the answers travel inside the file so that it can score with no internet.
  • Check a file reads text. It cannot follow code that hides what it does, and it cannot prove that software is free of mistakes. Reading the script goes further: it is one script and it is not minified.
  • On an iPad, the Files app shows a preview that does not run the file, so an iPad may need the file served from a web address, such as the school's learning platform. Reported, not yet tested by us.
  • The file has had no formal accessibility audit yet.
